# שער SMS ישראלי

## הנחיות

### שלב 1: אימות מספר טלפון ישראלי

תשתמשו ב-`scripts/validate_phone.py`. הסקריפט מקודד את תוכנית המספור העדכנית, ובדיוק בשלוש הנקודות שבהן regex שנכתב ביד כמעט תמיד נכשל: הוא מקבל מספרים קטועים, הוא מקבל רשתות פלסטיניות שחולקות את קידומת +972, והוא מקבל אורך קו נייח שלא קיים.

טבלת ההקצאה שהסקריפט אוכף:

| טווח | משמעות | ספרות מקומיות |
|-------|---------|--------------|
| 050, 051, 052, 053, 054, 055, 058 | סלולר ישראלי | 10 |
| 056 (Ooredoo Palestine), 059 (Jawwal) | סלולר פלסטיני, נדחה | 10 |
| 057 | קידומת שיצאה משימוש (Hot mobile השתמשה בה עד נובמבר 2014), נדחית | 10 |
| 02, 03, 04, 08, 09 | קו נייח גיאוגרפי | 9 |
| 072 עד 079 | נייח לא גיאוגרפי ו-VoIP (070 ו-071 מחוץ לתוכנית המספור) | 10 |

שתי מלכודות ששווה לקרוא בשמן:

1. תכתבו את קידומות הסלולר כרשימת חלופות מפורשת, לעולם לא כטווח תווים `05[0-8]`. הטווח אמנם מייצר כמעט את הקבוצה הנכונה היום, אבל הוא מכניס בשקט את 056 ואת 057, וברגע שמישהו ירחיב אותו ל-`05[0-9]` הוא יכניס גם את 059. גם 056 וגם 059 הן רשתות פלסטיניות.
2. נפילה לענף הנייח בסגנון `0[2-9]` עם אורך רופף תחזיר פנימה כל מספר 05 שענף הסלולר בדיוק דחה, וכך תבטל כל שמירה על הסלולר שמעליה. תעגנו את האורך ותוודאו ש-05 לא מגיע לענף הזה בכלל.

מספר טלפון תקין הוא לא בהכרח יעד תקין ל-SMS. קווים נייחים (גיאוגרפיים ו-072 עד 079) עוברים אימות כמספרי טלפון, אבל בדרך כלל לא יכולים לקבל SMS: טוויליו דוחה אותם מיד עם שגיאה 21614. לכן `scripts/send_sms.py` מסרב לשלוח לנמען נייח אלא אם מעבירים `--allow-landline`, ו-`scripts/validate_phone.py --sms-check` מחזיר קוד יציאה 2 עבור נייח.

```python
import re

MOBILE_RE = re.compile(r'^(?:050|051|052|053|054|055|058)\d{7}$')
LANDLINE_GEO_RE = re.compile(r'^0(?:2|3|4|8|9)\d{7}$')
LANDLINE_NONGEO_RE = re.compile(r'^07[2-9]\d{7}$')


def validate_israeli_phone(phone: str) -> tuple[bool, str]:
    raw = re.sub(r'[\s\-\(\)\.]', '', phone)
    clean = raw
    if clean.startswith('+972'):
        clean = '0' + clean[4:]
    elif clean.startswith('972'):
        clean = '0' + clean[3:]

    # In +972 form the national trunk 0 is dropped.
    if (raw.startswith('+972') or raw.startswith('972')) and clean.startswith('00'):
        return False, 'Extra leading zero: use +972501234567, not +9720501234567'

    if MOBILE_RE.match(clean):
        return True, '+972' + clean[1:]
    if clean[:3] in ('056', '059'):
        return False, 'Palestinian network (056 Ooredoo, 059 Jawwal), not Israeli'
    if LANDLINE_GEO_RE.match(clean) or LANDLINE_NONGEO_RE.match(clean):
        return True, '+972' + clean[1:]
    return False, 'Invalid Israeli phone number'
```

### שלב 2: תחשבו סגמנטים לפני שאתם מחשבים עלות

זה הדבר היקר ביותר לטעות בו, והוא חשבון פשוט ולא עניין של דעה. הספק מחייב לפי סגמנט, לא לפי שליחה.

| קידוד | סגמנט בודד | לסגמנט כשההודעה מתפצלת |
|----------|----------------|------------------------|
| GSM-7 (לטינית) | 160 | 153 |
| UCS-2 (עברית, או כל תו שאינו GSM-7) | 70 | 67 |

אות עברית אחת בכל מקום בגוף ההודעה מורידה את כל ההודעה ל-UCS-2 וחותכת את הקיבולת ביותר מחצי. הודעה עברית של 140 תווים היא שלושה סגמנטים ולא אחד, ולכן תקציב שנבנה מספירת תווים בלבד נמוך פי שניים עד שלושה מהעלות האמיתית. רוב האימוג'י עושים את אותו דבר ועולים שתי יחידות כל אחד. כך גם מירכאות מסולסלות, מקפים בינוניים ורווחים קשיחים שמודבקים מ-Word לטקסט לועזי: הם מחוץ ל-GSM-7 ומעבירים בשקט את כל ההודעה ל-UCS-2.

תריצו הערכה לפני השליחה:

```bash
python scripts/send_sms.py --estimate \
    --message "שלום, ההזמנה שלך יצאה למשלוח" \
    --price-per-segment 0.09 --recipients 5000
```

הפונקציה `segment_count()` בתוך `scripts/send_sms.py` ניתנת לייבוא אם אתם רוצים את אותו חישוב בתוך קוד התקצוב שלכם.

חברת Bird היא מי שנקראה קודם MessageBird; שינוי השם הושלם לפני 2025, ולכן אזכור של MessageBird במדריכים ישנים מתייחס לאותו ספק.

### שלב 4: שליחת SMS

**ספק InforUMobile (JSON REST, חוזה v2 הנוכחי):**

ההזדהות היא HTTP Basic על `username:API-token`. שימו לב שמדובר בטוקן ה-API ולא בסיסמת החשבון, ושערך הכותרת חייב להיות מקודד base64 באמת. גוף הבקשה עטוף תחת מפתח עליון `Data`. התשובות מחזירות `StatusId` ו-`StatusDescription`.

```python
import base64
import os
import requests


def send_sms_inforu(to: str, message: str, sender: str) -> dict:
    """Send SMS via the InforU v2 JSON endpoint."""
    creds = f'{os.environ.get("INFORU_USER", "")}:{os.environ.get("INFORU_API_TOKEN", "")}'
    token = base64.b64encode(creds.encode("utf-8")).decode("ascii")

    response = requests.post(
        "https://capi.inforu.co.il/api/v2/SMS/SendSms",
        headers={
            "Authorization": f"Basic {token}",
            "Content-Type": "application/json; charset=utf-8",
        },
        json={
            "Data": {
                "Message": message,
                "Recipients": [{"Phone": to}],  # local form, e.g. 0541234567
                "Settings": {"Sender": sender},
            }
        },
        timeout=15,
    )
    return response.json()  # StatusId 1 = accepted
```

בדוגמאות ה-SMS של InforU הנמען מופיע תמיד בפורמט מקומי (`0541234567`), ולכן שלחו אותו כך ולא בפורמט `972...`. מגבלת הקצב המתועדת היא 30 קריאות בשנייה; קריאות מעבר לכך מחזירות `-429` (HTTP 429 Too Many Requests), ולכן לולאת שליחה המונית צריכה ויסות קצב.

**SMS4Free (JSON REST v2):**

נקודת הקצה החיה היא `https://api.sms4free.co.il/ApiSMS/v2/SendSMS`. שני דברים שוברים כאן קוד תמים:

- הכתובת הישנה `www.sms4free.co.il/ApiSMS/SendSMS` מפנה היום לדף הבית. היא מתה כ-API.
- הגרסאות v1 ו-v2 מחזירות טיפוסים שונים. גרסה v1 מחזירה מספר שלם בגוף התשובה, וגרסה v2 מחזירה מעטפת JSON עם `status` ו-`message`. קוד שבודק `response.text == "1"` שגוי מול v2, ומול v1 הוא מדווח על כישלון בכל שליחה מוצלחת לכמה נמענים, כי ערך חיובי הוא מספר ההודעות שהתקבלו ולא הספרה 1.

תיעוד המפתחים של SMS4Free מפרסם את טבלת הסטטוסים: ערך חיובי הוא מספר הנמענים שהתקבלו לשליחה, `0` שגיאה כללית, `-1` מפתח, שם משתמש או סיסמה שגויים, `-2` מזהה שולח לא תקין, `-3` לא נמצאו נמענים, `-4` יתרת הודעות נמוכה, `-5` הודעה לא מתאימה, `-6` מספר שולח לא עבר אימות ראשוני. קוד HTTP 200 אינו אישור בפני עצמו; תבדקו תמיד את `status` ותציגו לצידו את שדה `message` של ה-API. ההזדהות היא שלושה שדות בגוף הבקשה: `user` (מספר הנייד שאיתו נרשמתם), `pass` (סיסמת החשבון) ו-`key` (מפתח ה-API האישי מדף ה-API בחשבון). בתקופת הניסיון החינמית השולח נעול למספר שאיתו נרשמתם, ולכן שולח מותאם אישית נכשל עם `-2` עד שרוכשים חבילה.

**ספק 019 SMS:** מתועד בכתובת https://docs.019sms.co.il/sms/ עם כתובת בסיס `https://019sms.co.il/api`, תמיכה ב-XML או JSON, והזדהות בטוקן. יש גם סביבת בדיקה בכתובת `https://019sms.co.il/api/test`, שמשקפת את הבקשה האמיתית בלי לבצע את הפעולה. תשתמשו בה כדי לאמת את מבנה הבקשה לפני שאתם שורפים קרדיטים; זה הדבר השימושי ביותר ברשימה הזו למפתח, וגם הכי מפוספס.

הספקים חלוקים גם על פורמט הנמען וגם על מה נחשב הצלחה, ולכן לעולם אל תשתמשו במפענח של ספק אחד עבור ספק אחר:

| ספק | פורמט נמען | סימן הצלחה |
|-----|------------|------------|
| InforU | מקומי, `0541234567` (הפורמט היחיד בדוגמאות ה-SMS שלה) | `StatusId` 1 |
| SMS4Free | `05XXXXXXXX`, `9725XXXXXXXX` או `+9725XXXXXXXX` | `status` גדול מ-0 (מספר הנמענים) |
| 019 SMS | `5xxxxxxx` או `05xxxxxxx` | `status` 0 |
| Twilio | E.164, `+972541234567` | HTTP 201 |

**ספק Twilio:** שירות Programmable Messaging סטנדרטי. לישראל יש כללים תפעוליים שבולעים תעבורה בשקט אם מתעלמים מהם, והם מפורטים במלכודות.

### שלב 5: דוחות מסירה (DLR)

בסקריפט המצורף אין דגל לבדיקת סטטוס מסירה; סטטוס המסירה הוא קריאה נפרדת או webhook אצל הספק. איפה לחפש:

- אצל InforU: תשאלו במחזוריות (polling) את https://capi.inforu.co.il/api/v2/PullData עם `Data.Type` בערך `DeliveryNotificationSMS` וגודל אצווה, או תבקשו מ-InforU לדחוף כל דוח לכתובת שלכם באמצעות `Settings.DeliveryNotificationUrl` בבקשת השליחה.
- אצל SMS4Free: תעבירו `returnUrl` ו-`usermsgid` בבקשת השליחה; SMS4Free שולחת אז POST בקידוד טופס עם `to`, `status` ו-`msgId` לכתובת הזו. סטטוסים נפוצים: 1 נמסר, 5 לא נמסר, 6 מספר כשר.
- אצל 019 SMS: ראו את תיעוד ה-API המקושר למעלה.
- אצל Twilio: webhook מסוג `StatusCallback` על ההודעה.

### שלב 6: הקשחת OTP

הסקיל הזה משווק OTP כתרחיש שימוש מרכזי, ולכן תתייחסו לבקרות האבטחה כחובה ולא כרשות:

- תגבילו קצב לפי מספר היעד, לא רק לפי כתובת IP או לפי חשבון.
- תגבילו את מספר ניסיונות האימות לכל קוד, ואז תבטלו את הקוד.
- תתנו לכל קוד תוקף קצר ותמחקו אותו בשימוש המוצלח הראשון כדי שלא יהיה ניתן לשחזור.
- תשוו בהשוואה בזמן קבוע, לעולם לא ב-`==` על המחרוזת הגולמית.
- לעולם אל תכתבו את הקוד ללוגים, לאנליטיקס או למערכת ניטור השגיאות.
- תהפכו את השליחה לאידמפוטנטית באמצעות מזהה בקשה ייחודי, כך שקריאת HTTP שנשלחת שוב תשלח את אותו הקוד במקום לייצר חדש. בלי זה, לולאת ניסיון חוזר הופכת גם למחולל חיובים כפולים וגם למחולל קודים כפולים, והמשתמש מקבל כמה קודים תקפים בבת אחת.

אותו כלל אידמפוטנטיות חל על שליחה המונית: תצמידו לכל שליחה לנמען מזהה ייחודי כך שניסיון חוזר אחרי כישלון חלקי לא יחייב ולא ימסור את האצווה פעמיים.

### שלב 7: רשימת בדיקה לעמידה בתקנות (חוק הספאם + תיקון 13 לחוק הגנת הפרטיות)

שליחת SMS מסחרי בישראל כפופה לסעיף 30א לחוק התקשורת (בזק ושידורים), הידוע כחוק הספאם, ומאז 14 באוגוסט 2025 גם לתיקון 13 לחוק הגנת הפרטיות, שהחמיר את החובות על מי שמעבד מידע אישי.

הודעת SMS היא דבר פרסומת כשהתכלית שלה מסחרית: החוק מגדיר זאת כמסר המופץ באופן מסחרי, שמטרתו לעודד רכישת מוצר או שירות או לעודד הוצאת כספים בדרך אחרת. ההגדרה חלה גם על מסר לציבור הרחב שמטרתו בקשת תרומה או תעמולה, אבל החוק מגדיר תעמולה כך שהיא אינה כוללת מסר פוליטי, ובכלל זה תעמולת בחירות. חלופה שלישית תופסת מסר לציבור הרחב שמציע לנמען להתקשר למספר טלפון מסוים לשם קבלת מסר כלשהו.

לפני שליחת SMS מסחרי:

- [ ] הנמען נתן הסכמה מפורשת מראש בכתב (פעולה אקטיבית, לא תיבה מסומנת מראש), או שאתם עומדים במסלול הלקוח הקיים בסעיף הבא
- [ ] מסלול הלקוח הקיים, כל התנאים יחד: הנמען מסר את פרטיו במהלך רכישה או במהלך משא ומתן לרכישה; אמרתם לו באותו מעמד שהפרטים ישמשו למשלוח פרסומת; נתתם לו הזדמנות לסרב והוא לא סירב; והפרסומת מתייחסת למוצר או לשירות מסוג דומה לאותה רכישה. חסר ולו תנאי אחד, וחוזרים לדרישת הסכמה מפורשת
- [ ] תיעוד הסכמה: מי, למה הסכים, מתי, באיזה ערוץ
- [ ] תוכן ההודעה: בהודעת מסר קצר החוק דורש את שם המפרסם ואת דרכי יצירת הקשר לצורך מתן הודעת סירוב. הרשימה הרחבה שחלה על ערוצים אחרים (המילה פרסומת בתחילת ההודעה, וכן שם, כתובת ודרכי יצירת קשר, וכן זכות הסירוב) מצומצמת עבור מסרונים לשם ולדרכי יצירת הקשר לצורך סירוב בלבד. הוספת המילה פרסומת היא נוהג מקובל ואינה מזיקה במהות, אבל סעיף המסרונים עצמו מונה רק את שני הפרטים האלה
- [ ] הודעת הסירוב חינם למעט עלות משלוח ההודעה עצמה, והנמען הוא שבוחר אם לסרב בכתב או באותו ערוץ שבו הגיעה הפרסומת. לכן תשובת `עצור` למסרון חייבת לעבוד בפועל, ולא רק קישור. אי אפשר בכלל להשיב לזיהוי שולח טקסטואלי (אלפא-נומרי), ולכן הודעה שיווקית שנשלחת ממנו צריכה לכלול בגוף ההודעה מספר להשבה או את מנגנון ההסרה המובנה של הספק
- [ ] מכבדים כל בקשת הסרה; שליחה אחרי סירוב שוללת כל טענת תום לב
- [ ] בעסקה מתמשכת, סיום ההתקשרות נחשב כשלעצמו להודעת סירוב
- [ ] מספרי הטלפון נאספו כדין לפי תיקון 13 (תכלית, מינימום מידע, אבטחה), וההודעה לפי סעיף 11 נמסרה בעת איסוף המספר
- [ ] דיוור ישיר לפי חוק הגנת הפרטיות, משטר נפרד מחוק הספאם: פנייה אישית לאדם על סמך השתייכותו לקבוצת אוכלוסין שנקבעה לפי אפיון אחד או יותר של אנשים שבמאגר מידע (למשל "לקוחות שקנו בשנה האחרונה" או "לקוחות בחיפה"). סעיף 17ו(א) דורש אז שכל פנייה תכיל באופן ברור ובולט: ציון שהפנייה היא בדיוור ישיר (וגם מספר הרישום של המאגר המשמש לשירותי דיוור ישיר, אם הוא רשום; מאז תיקון 13 חובת הרישום חלה רק במקרים מצומצמים יותר, כמו מאגר שמטרתו העיקרית מסירת מידע אישי לאחרים, ולכן לעסקים רבים שפונים ללקוחות שלהם אין מספר כזה לציין), הודעה על זכות הנמען להימחק מהמאגר עם המען לבקשה, וזהותו ומענו של בעל השליטה במאגר והמקורות שמהם קיבל את המידע. בניגוד לחוק הספאם, אין לרשימה הזו גרסה מקוצרת למסרונים, ולכן ההתאמה שלה ל-SMS (בגוף ההודעה או דרך קישור) היא החלטה שכדאי לקבל עם עורך דין. לפי סעיף 23כו(ג), שנוסף בתיקון 13, הרשות להגנת הפרטיות רשאית להטיל עיצום כספי של 50 ש"ח (מתואם: 51.18 ש"ח בשנת 2026) כפול מספר הנמענים, ולא פחות מ-30,000 ש"ח (30,710 ש"ח בשנת 2026); אותו עיצום לפי אדם חל גם על איסוף מספר בלי ההודעה לפי סעיף 11. אם שליחה לא מפולחת לכל רשימת הלקוחות היא דיוור ישיר זו שאלה שנויה במחלוקת, ולכן אל תניחו שלא.
- [ ] אין העברה לחו"ל של רשימות נמענים בלי הגנה הולמת
- [ ] שליחה בשעות סבירות (להימנע משבת לנמענים דתיים, להימנע משעות לילה מאוחרות)
- [ ] מודעות לסנקציות: כאשר הפרסומת שוגרה ביודעין, בית המשפט רשאי לפסוק פיצויים שאינם תלויים בנזק, בסכום שלא יעלה על 1,000 שקלים חדשים לכל פרסומת. זו תקרה נתונה לשיקול דעת ולא תעריף אוטומטי. שני דברים מחמירים את זה בפועל: קיימת חזקה שהמפרסם פעל ביודעין אלא אם יוכיח אחרת, ואת החזקה הזו אי אפשר לסתור כלל בשלושה מקרים: ההודעה נשלחה אחרי הודעת סירוב; המפרסם שלח בעבר לאותו נמען פרסומת בניגוד לחוק, גם אם לא ביודעין; או שהמספר הגיע מרשימה שהורכבה ברצף אקראי. בקמפיין חודשי חוזר המקרה השני אומר ששליחה פסולה אחת מכתימה כל שליחה מאוחרת לאותו נמען
- [ ] חשיפה פלילית ואישית: שליחה בלי הסכמה היא גם עבירה פלילית שדינה קנס, ומנהל התאגיד ומי שאחראי על השיווק חייבים לפקח כדי למנוע אותה. אם התאגיד עבר את העבירה, חזקה שנושאי המשרה האלה הפרו את חובתם אלא אם יראו שעשו כל שניתן

## דוגמאות

### דוגמה 1: שליחת OTP
המשתמש אומר: "שלח קוד אימות למספר נייד ישראלי."
תוצאה: יצירת קוד בן 6 ספרות, שליחה דרך API של הספק, החלת בקרות ההקשחה משלב 6, וביטול הקוד ב-backend אחרי 5 עד 10 דקות.

בהיבט המשפטי, תיזהרו מהטענה הרווחת שהודעות OTP והודעות שירות פשוט פטורות. אין בחוק פטור מפורש להודעת שירות. המבחן הוא תכלית ההודעה, ולכן הודעה טרנזקציונית אמיתית שהמשתמש עצמו יזם נמצאת מחוץ להגדרה, אבל ברגע שאותה הודעה נושאת לוגו, סלוגן, מבצע או קישור שיווקי היא עלולה להפוך לדבר פרסומת ולחזור תחת דרישת ההסכמה. תשמרו על הודעות טרנזקציוניות טרנזקציוניות בלבד.

### דוגמה 2: פורמט מספר טלפון
המשתמש אומר: "המר את 054-1234567 לפורמט בינלאומי."
תוצאה: `+972541234567`. שימו לב שהאפס המוביל יורד, ולכן `+9720541234567` שגוי.

### דוגמה 3: SMS שיווקי המוני
המשתמש אומר: "שלח SMS קידום מכירות לרשימת הלקוחות שלי על מבצע חג."
פעולות:
1. תאמתו כל מספר עם `scripts/validate_phone.py` ותסננו קידומות פלסטיניות.
2. תריצו את הערכת הסגמנטים על הנוסח הסופי ותתקצבו לפי סגמנטים ולא לפי תווים.
3. תסננו את הרשימה מול טבלת ההסרות ומול תיעוד ההסכמה או מסלול הלקוח הקיים.
4. תכללו את שם המפרסם ומנגנון הסרה עובד באותו ערוץ. אם הרשימה נבחרה ממאגר הלקוחות לפי אפיון, תכללו גם את פרטי הדיוור הישיר משלב 7.
5. תתזמנו לשעות עסקים בישראל (להימנע משישי אחר הצהריים ועד מוצאי שבת, להימנע מחגי ישראל ב-B2C).
6. תשלחו עם מפתחות אידמפוטנטיות לכל נמען ותזרימו את דוחות המסירה חזרה ל-CRM.
תוצאה: קמפיין שנבדק מול סעיפי חוק הספאם וחוק הגנת הפרטיות בשלב 7, עם מספר עלות שתואם את החשבונית.

## משאבים מצורפים

### סקריפטים
- הסקריפט `scripts/send_sms.py` שולח SMS דרך SMS4Free, Twilio או InforUMobile, ומחשב סגמנטים ב-GSM-7 לעומת UCS-2 ועלות משוערת באמצעות `--estimate`. פרטי ההזדהות מגיעים מארגומנטים בשורת הפקודה או ממשתני סביבה (SMS_API_KEY, TWILIO_ACCOUNT_SID וכו'), וכתובת השרת של כל ספק קבועה בקוד. הוא מסרב לנמען נייח אלא אם מעבירים `--allow-landline`. הוא אינו בודק סטטוס מסירה; ראו שלב 5. הרצה: `python scripts/send_sms.py --help`
- הסקריפט `scripts/validate_phone.py` מאמת ומנרמל מספרי טלפון ישראליים מכל פורמט נפוץ לפורמט בינלאומי +972, מבחין בין סלולר לנייח גיאוגרפי ולא גיאוגרפי, ודוחה קידומות פלסטיניות וקידומות שיצאו משימוש עם הודעת הסבר. הדגל `--sms-check` מחזיר קוד יציאה 2 עבור נייח תקין, כי נייח אינו יעד ל-SMS. הרצה: `python scripts/validate_phone.py --help`

## מלכודות נפוצות

- מספרי סלולר ישראליים הם 10 ספרות שמתחילות ב-05X. סוכנים בודקים מול פורמטים אמריקאיים, או משאירים את האפס המוביל בהמרה ל-+972. הצורה הנכונה מורידה אותו.
- הקידומות 056 ו-059 הן רשתות פלסטיניות (Ooredoo Palestine ו-Jawwal) שחולקות את קידומת +972. ביטוי רגולרי שנכתב כ-`05[0-9]`, או כטווח `05[0-8]`, מקבל אותן בשקט. טוויליו מנתבת את שתי הקידומות האלה דרך הרשאת ה-geo של פלסטין ולא של ישראל, תחת תעריף ומדיניות שונים.
- ענף הנייח באימות הוא המקום שבו כל השמירות על הסלולר מתות. הביטוי `0[2-9]\d{7,8}` מקבל מספר סלולר קטוע בן 9 ספרות כנייח תקין, וכך סוכן שכביכול אימת את המספר עדיין שולח למספר שלא יכול לקבל.
- עברית היא UCS-2: 70 תווים בסגמנט אחד, 67 לסגמנט אחרי פיצול. מודל עלות שנבנה על נתון 160 התווים הלטיני נמוך פי שניים עד שלושה מהעלות האמיתית בקמפיין עברי. תו עברי אחד בהודעה לטינית מוריד את כל ההודעה.
- זיהוי שולח בישראל אינו מרשם ממשלתי, ואין פורטל של משרד התקשורת להגיש אליו בקשה. החובות מוטלות על הספק שלכם, בשתי שכבות. ראשית, לפי רגולציה של משרד התקשורת שנכנסה לתוקף ב-3.1.2021 ונועדה למנוע התחזות בזיהוי השולח, זיהוי שולח שהוא מספר טלפון נייד או נייח אמיתי דורש אימות בעלות חד פעמי לפני השליחה הראשונה (זיהוי שולח שמי באותיות באנגלית, שליחה ממספר חסוי ומספר וירטואלי שהספק סיפק פטורים מבדיקת המספר הזו). שנית, לפי רפורמת הפישינג שעליה החליט משרד התקשורת באוקטובר 2022, עסק שמפיץ מסרונים דרך מערכת הפצה חייב לעבור אימות זהות חזק מול הספק, למשל שיחת וידאו עם הצגת מסמכים מזהים ואימות של כרטיס האשראי המשלם; ספקים מדווחים ששמות שולח טקסטואליים (אלפא-נומריים) מוגבלים כך מאז 25.4.2023. תקצבו זמן לתהליך הזה לפני השקה. ספקים בינלאומיים דורשים בנוסף רישום מוקדם משלהם לזיהוי אלפא-נומרי, שטוויליו מציינת שאורך כשבוע בישראל.
- כללים תפעוליים של Twilio בישראל שגורמים להודעות להיעלם בלי שגיאה ברורה: מספרים קצרים אינם נתמכים בישראל; תעבורה בינלאומית שנשלחת מעל מספרים מקומיים ארוכים נחסמת אקטיבית על ידי המפעילים; שימוש במספר מקומי שאינו אמיתי כזיהוי שולח (למשל מספר הנייח של חברה) אסור בישראל וככל הנראה יידחה על ידי מפעיל הרשת; וברשתות גולן ועזי תקשורת זיהוי שולח נומרי מוחלף בזיהוי אלפא-נומרי גנרי מחוץ לפלטפורמה של טוויליו, כך שהמספר שבחרתם בקפידה אינו מה שהנמען רואה.
- טלפונים כשרים (מספר כשר) חוסמים SMS. קוד OTP שנשלח לטלפון כזה הולך לאיבוד בשקט, אלא אם הספק ממיר אותו לשיחה קולית: SMS4Free עושה זאת אוטומטית ומדווחת בדוח המסירה סטטוס 6 "מספר כשר". תציעו חלופת OTP קולית במקום לקודד טווחי מספרים כשרים, שמשתנים.
- מוצר ה-SMS של InforU עבר לחוזה JSON בגרסה v2 על host שונה מנקודת הקצה הישנה של XML. שליחת גוף JSON חדש לכתובת ישנה, או שליחת טוקן ה-API בלי קידוד base64 בכותרת ה-Basic, שתיהן נכשלות.
- הגרסאות v1 ו-v2 של SMS4Free מחזירות טיפוסי תשובה שונים מכתובות כמעט זהות. העתקה של המפענח הלא נכון גורמת לכל שליחה להיראות ככישלון.
- שליחה בשבת היא פרקטיקה גרועה ל-B2C בישראל ומקור תכוף לתלונות.
- הודעת OTP אינה פטורה אוטומטית מחוק הספאם. הוספת שורה שיווקית או קישור שיווקי להודעת אימות עלולה להפוך אותה לפרסומת.

## פתרון בעיות

### שגיאה: "ההודעה לא נמסרה"
סיבה: מספר לא תקין, חסימת מפעיל, חריגה ממכסה, או זיהוי שולח שלא עבר אימות בעלות.
פתרון: תאמתו מחדש עם הסקריפט המצורף, תוודאו פרטי הזדהות, ותמשכו את דוח המסירה (שלב 5) במקום לנחש לפי תשובת השליחה. תשובת השליחה אומרת רק שהשער קיבל את ההודעה.

### שגיאה: הודעות נעלמות עם תשובת הצלחה (Twilio, ישראל)
סיבה: בדרך כלל אחד הכללים הישראליים. מספרים קצרים אינם נתמכים; תעבורה בינלאומית מעל מספרים מקומיים ארוכים נחסמת על ידי המפעילים; מספר מקומי שאינו אמיתי (כמו נייח של חברה) כזיהוי שולח נדחה על ידי המפעיל; או שהנמען ברשת גולן או עזי תקשורת, שבהן זיהוי שולח נומרי מוחלף בזיהוי אלפא-נומרי גנרי. אם ה-API עצמו החזיר שגיאה 21614, הנמען הוא קו נייח, שלא יכול לקבל SMS.
פתרון: תעברו לזיהוי שולח אלפא-נומרי רשום, ותנתבו תעבורה ישראלית דרך ספק ישראלי אם אחוז המסירה חשוב לכם יותר מאינטגרציה גלובלית אחת.

### שגיאה: "זיהוי השולח נדחה"
סיבה: זיהוי שולח נומרי שלא השלים את אימות הבעלות החד פעמי שהנהיגה רגולציית 3.1.2021 (ב-SMS4Free סטטוס `-6`), זיהוי אלפא-נומרי שנעשה בו שימוש לפני שהחשבון עבר את אימות הזהות או הרישום המוקדם אצל הספק, או שולח מותאם אישית בתקופת ניסיון חינמית (ב-SMS4Free סטטוס `-2`).
פתרון: תשלימו את האימות מול הספק. מספר שולח נייד מאומת דרך קישור שנשלח לאותו מכשיר; מספר שולח נייח מאומת בשיחה מאותו קו. עד להשלמת הרישום, תיפלו חזרה לזיהוי ברירת המחדל של הספק.

### שגיאה: "תווים עבריים מעוותים ב-SMS"
סיבה: ההודעה לא נשלחה כ-UCS-2, או נקטעה במגבלת אורך לטינית.
פתרון: תשלחו ב-UCS-2 במפורש. רוב הספקים הישראליים מזהים עברית אוטומטית. תוודאו במכשיר אמיתי ולא בסימולטור.

### שגיאה: החשבונית כפולה מההערכה
סיבה: תקצוב לפי הודעה ולא לפי סגמנט בתעבורה עברית.
פתרון: תריצו `python scripts/send_sms.py --estimate` על הנוסח הסופי, ותוודאו מול הספק אם ההצעה היא לפי הודעה או לפי סגמנט.

### שגיאה: משתמשים מקבלים כמה קודי OTP תקפים בבת אחת
סיבה: שליחה שנשלחה שוב ומייצרת קוד חדש בכל פעם.
פתרון: תהפכו את השליחה לאידמפוטנטית לפי מזהה בקשה כמתואר בשלב 6, ותבטלו את הקוד הקודם בכל פעם שמונפק קוד חדש כדין.
